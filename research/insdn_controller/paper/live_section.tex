\section{A Forwarding-Application Case Study}\label{sec:live}
InSDN shows one forwarding configuration. To see whether what the controller observes depends on the forwarding
application, we built a small testbed (Mininet, one Open vSwitch switch, six hosts; a Ryu OpenFlow~1.3 learning
switch with a configurable entry granularity) and recorded its control channel with the same parser. The three modes
install, for each learned destination, an entry matching (i) the MAC pair; (ii) the 5-tuple for TCP/UDP with a 10\,s
idle timeout; or (iii) the 5-tuple with a 2\,s idle timeout applied to all entries. In the two 5-tuple modes, other IP
traffic receives an (src, dst, protocol) entry and ARP an ARP-only entry, so a coarse entry for one protocol cannot
match another. The controller polls flow statistics every second. Traffic is benign only and generated by the same
program with the same random seeds in every mode (request timing still differs): five hosts repeatedly fetch files of
16\,KB to 1\,MB from an HTTP server (80\%) or ping it (20\%) with random pacing for 90\,s (captures span
$\sim$99\,s including start-up). Each mode was run 10 times (seeds 0--9), reporting mean and 95\% $t$-interval over runs
(Table~\ref{tab:live}); the 30 runs completed 26\,891 requests, of which 41 failed (below). We repeated the study on a
loop-free three-switch chain (Table~\ref{tab:live_l3}, below).

\textbf{Granularity sets the PacketIn volume.} MAC-pair mode produced $12.3\pm2.3$ TCP PacketIns per run, against
$10\,422\pm202$ (10\,s idle) and $10\,392\pm249$ (2\,s idle) under per-flow forwarding: 665$\times$ to 1\,752$\times$ (10\,s idle)
and 668$\times$ to 1\,780$\times$ (2\,s idle) more in each of the ten paired runs (larger in 10 of 10; two-sided sign-test $p=0.002$). That is about 11--12 TCP PacketIns per
completed request, so each connection is punted repeatedly; the most likely cause is packets that arrive before the
FlowMod takes effect (we install entries without a barrier and send full packets), but we did not isolate this
mechanism. FlowMods (19.1 vs.\ about 10\,440 and 10\,560 per run) track the PacketIns and are not independent evidence. The
MAC-pair result is a replication: the same mode in the first, flawed campaign gave $11.0\pm4.1$. Seeds 0--4 are the
earlier five runs per mode (reported in the previous version of this study); seeds 5--9 were added later.

\textbf{Idle timeout sets what a poller sees.} Per-flow entries returned per statistics reply fell from $153.1\pm2.4$
to $36.9\pm0.5$ when the idle timeout dropped from 10\,s to 2\,s, a ratio of 0.234 to 0.246 in all ten pairs: entries
expire between polls, so a 1\,s poller sees about a quarter as many. The result is close to what a shorter timeout
implies; its value is the size of the loss for a realistic polling interval. In MAC-pair mode the replies contain only
the table-miss rule and MAC-pair entries ($9.5\pm0.03$ per reply); no entry matches IP or transport fields, as in
InSDN (whose ONOS additionally installed \texttt{eth\_type} punt rules).

\textbf{A flawed first campaign.} Our first application installed MAC-pair entries for ping and ARP in every mode;
these also match later TCP between the same hosts, so most connections never reached the controller and per-flow mode
produced only $43.4\pm30.1$ TCP PacketIns per run (4$\times$ MAC-pair) with a wide interval. The original application
is archived as \texttt{ryu\_fwd\_v1.py}. We report it because it shows how an overlapping coarse entry hides traffic
from the controller by two orders of magnitude, independently of the forwarding mode's nominal granularity.

\textbf{Reliability.} One run (5-tuple, 2\,s idle, seed 4) had 41 failed requests (7--10 per client); the other 29
one-switch runs and all 30 three-switch runs had none. The run did not reproduce, and its failures were spread evenly over
all five clients, which is consistent with a short stall of the shared path or controller rather than one client. The cause
is not established (the failure reasons were not logged in that run; later runs log them). The run is included in all figures.

\textbf{A second topology.} On a three-switch chain (hosts h1--h6, server two hops from h1 and h2; 10 runs per mode,
26\,826 requests, none failed) the contrast holds (Table~\ref{tab:live_l3}): $18.0\pm5.0$ TCP PacketIns per run under
MAC-pair against $10\,881\pm794$ and $10\,676\pm804$ under per-flow forwarding (391$\times$ to 1\,509$\times$ in every
paired run), and the per-flow entries a 1\,s poller sees per reply fall from $112.4\pm2.3$ to $27.0\pm0.4$ (ratio 0.235 to
0.245). The ratio is smaller than on one switch because the MAC-pair baseline rises with the extra hops (18.0 vs.\ 12.3).

\textbf{A stock Ryu application.} To check that the MAC-pair behaviour is not an artefact of our own application, we ran Ryu's
unmodified \texttt{simple\_switch\_13} on the same one-switch topology (5 runs of 60\,s; 2\,982 requests, none failed). Of 91 FlowMods, 86
match \texttt{(in\_port, eth\_dst, eth\_src)} and 5 are the table-miss rule; none matches IP or transport fields. The controller
received 71, 69, 76, 76 and 76 PacketIns per run (mean 73.6, all protocols). Like ONOS's \texttt{fwd}, this application installs MAC-pair
entries; this follows from the application's code, and it does not test OpenDaylight, ONOS under other applications, or any production
deployment.

\textbf{Scope.} This is a testbed with at most three switches with one forwarding application and benign traffic only; we run no
attacks or detectors in it. The mode contrast does not transfer to InSDN's ONOS, which punted about one packet per
target packet even with MAC-pair entries (\S\ref{sec:gap}), and no claim is made about detection accuracy under any
forwarding mode.
