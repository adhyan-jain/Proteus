\begin{abstract}
Machine-learning intrusion detection for Software-Defined Networks (SDN) is usually evaluated on flow-record benchmarks computed offline at end hosts. We audit the validity of this practice on InSDN, the public SDN benchmark that also ships the OpenFlow control-channel captures of its ONOS controller, with CICIDS2017 as an external reference. Decoding all 44 control-channel captures (7\,381\,679 messages) shows that no flow-table entry or FlowMod matches IP addresses or ports, so per-flow counters are absent; ONOS instead punts IPv4 packets to the controller (an IPv4 punt rule is present in 44 of 44 captures), and the controller receives 0.68--1.29 PacketIns per target-side packet in 9 of 12 attack scenarios. Flows reassembled from PacketIns reproduce packet totals on probing traffic but only 38\% and 45\% of the host-side totals on DoS and benign traffic. A controller-side MLP reaches 0.946 balanced accuracy on unseen captures, but InSDN records benign and attack traffic in separate sessions: an ``any IP PacketIn'' rule scores 0.995 within attack sessions, a host-identity rule learned on training captures alone reaches 0.734, and the MLP's features separate sessions at 0.940 after attack packets are removed, so the score cannot be read as attack detection. Under strict labelling, OVS DDoS and OVS brute-force contribute no attack windows and probing supplies 76\% of the rest. On flow features, random splits give 0.9998 (InSDN) and 0.9917 (CICIDS2017) balanced accuracy, whereas holding out source hosts gives $0.907\pm0.085$ (worst split 0.66) and $0.641\pm0.056$; the InSDN dispersion is consistent with which of eight dominant hosts is withheld. A targeted audit of 12 SDN-IDS papers finds none that reports a host-grouped split. All findings concern one SDN dataset and one controller. We propose seven evaluation guidelines and release the code and result files behind every reported number.
\end{abstract}

\section{Introduction}\label{sec:intro}
Software-Defined Networking (SDN) decouples network control logic from underlying forwarding hardware, enabling centralized programmability and dynamic flow management~\cite{kreutz2015sdn,mckeown2008openflow}. Motivated by the controller's global architectural view, a substantial literature proposes machine learning (ML) and deep learning Network Intrusion Detection Systems (NIDS) designed to secure SDN environments~\cite{elsayed2020insdn,ataa2024intrusion,ashikuzzaman2026sdnguardstack}.

Despite widespread interest, a methodological gap separates published evaluations from operational networking conditions. In practice, SDN intrusion detection research rarely interacts with an active SDN controller. Instead, researchers predominantly evaluate machine learning models on offline comma-separated value (CSV) benchmarks, such as InSDN~\cite{elsayed2020insdn} and CICIDS2017~\cite{sharafaldin2018cicids}. These benchmark tables consist of bidirectional 5-tuple flow summaries computed by feature extractors like CICFlowMeter~\cite{lashkari2017cicflowmeter} operating directly on full-packet captures obtained from network taps at end hosts. Standard pipelines train high-capacity classifiers on 80+ statistical features---including inter-arrival time moments, bidirectional packet length distributions, and cumulative TCP flag counts---and consistently report detection accuracies exceeding 99.5\%~\cite{optixgb2026,peerj2025intrusion,sajid2025ddos}.

This prevalent methodology suffers from two foundational threats to validity, illustrated conceptually in Fig.~\ref{fig:arch}:
\begin{enumerate}
    \item \textbf{The Controller Observability Disconnect:} An OpenFlow controller does not have native access to packet-level timing moments or fine-grained per-flow payload metrics. Under standard OpenFlow~1.3 reactive forwarding~\cite{onf2012openflow13}, the controller receives \texttt{PacketIn} messages for initial flow misses, issues \texttt{FlowMod} entries, and periodically polls aggregate flow statistics counters. Whether the controller's installed flow table entries actually capture fine-grained 5-tuple counters depends on the controller's forwarding application. If the controller installs wildcard or MAC-pair rules, granular 5-tuple statistical features cannot be constructed at the controller without either altering flow-table granularity (risking TCAM exhaustion) or streaming full payloads (risking control-channel saturation).
    \item \textbf{The Evaluation-Validity and Topology Leakage Disconnect:} In security machine learning, randomized train/test splits are known to suffer from severe data leakage when applied to benchmark datasets with repetitive traffic or homogenous host assignments~\cite{sommer2010outside,arp2022dos,engelen2021troubleshooting,flood2024baddesign}. When flows from the same IP address or session appear in both training and test partitions, models learn spurious host-specific shortcut representations rather than generalizable attack signatures~\cite{roy2026unmasking}. In SDN topologies with highly concentrated host structures, reported near-perfect accuracies may simply reflect the model's ability to recognize previously seen hosts rather than its capability to detect novel attackers.
\end{enumerate}

While prior studies have highlighted feature calculation discrepancies~\cite{sarhan2022standard,pinto2025flowexporter,pekar2024partial,pekar2024integrity} or identified data smells in general non-SDN datasets~\cite{flood2024baddesign}, the specific manifestation of these issues within SDN control-plane environments remains largely unquantified. Crucially, the InSDN dataset release included not only offline flow CSVs but also the raw PCAP files of the ONOS controller's OpenFlow~1.3 control channel across all evaluated scenarios~\cite{elsayed2020insdn}. This provides a unique, empirical opportunity to examine what an SDN controller actually observes during benchmark execution and to systematically audit evaluation validity.

In this work we audit controller observability and evaluation validity for SDN intrusion detection on InSDN. We make five contributions, each a measurement and not a new detector:
\begin{enumerate}
    \item \textbf{Control-channel characterization (\S\ref{sec:gap}).} We decode all 44 ONOS OpenFlow~1.3 captures shipped with InSDN. No flow-statistics entry (24\,437 MAC-pair and 80\,464 \texttt{eth\_type} observations) and none of the 3\,827 FlowMods matches IP addresses or transport ports, so the labelled 5-tuple flows are not available as switch counters under this configuration. An IPv4-to-controller punt rule is present in all 44 captures, and the controller receives 0.68--1.29 PacketIns per target-side packet in 9 of 12 attack scenarios.
    \item \textbf{What PacketIns can reconstruct (\S\ref{sec:gap}).} A software flow reassembler with CICFlowMeter's expiration rules, run on one capture per scenario, recovers packet counts and durations in some scenarios and not in others, and its output is incomplete relative to host-side records (Table~\ref{tab:recon}).
    \item \textbf{A validity analysis of controller-side detection (\S\ref{sec:method}--\S\ref{sec:confound}).} We show how label construction shapes the evaluated windows (Table~\ref{tab:deployment}) and compare a controller-side MLP with an ``any IP PacketIn'' rule, host-identity rules learned on training captures, and a session probe. The 0.946 score cannot be taken as evidence of attack detection, because the benchmark confounds session identity with the label.
    \item \textbf{A host-held-out audit (\S\ref{sec:audit}).} On InSDN and CICIDS2017, random flow splits give $\geq 0.9917$ balanced accuracy and source-host-held-out splits give $0.907\pm0.085$ and $0.641\pm0.056$. We log the hosts of every split, decompose the InSDN dispersion by dominant host (leave-one-host-out), and test deduplication. This confirms, on an SDN benchmark, leakage mechanisms described for other datasets~\cite{engelen2021troubleshooting,flood2024baddesign}; it is not a new principle.
    \item \textbf{Literature audit, recipes and forwarding mechanism (\S\ref{sec:live}, \S\ref{sec:lit_audit}).} A targeted audit of 12 SDN-IDS papers, four feature recipes approximating published proposals, and a Mininet/Ryu case study of how forwarding granularity and idle timeout change controller-visible telemetry.
\end{enumerate}
\textbf{Scope and non-claims.} We do not claim a deployable detector, evidence about controllers other than ONOS or datasets other than InSDN (CICIDS2017 is a non-SDN reference for the split analysis), or causal identification of the host effect. Section~\ref{sec:discussion} lists the threats to validity.

\section{Background and Related Work}\label{sec:relwork}
\subsection{SDN Control-Plane Mechanics and Telemetry}
In an OpenFlow~1.3 network~\cite{onf2012openflow13}, switches maintain flow tables containing match rules, priorities, timeouts, and actions. When a packet arrives at an OpenFlow switch without matching an existing flow entry, it triggers a table-miss event. Under reactive forwarding configurations, the switch encapsulates the packet header (or the entire frame) into an asynchronous \texttt{OFPT\_PACKET\_IN} message and transmits it across the secure control channel to the controller. The controller's forwarding logic processes the packet headers, determines the forwarding path, and responds with an \texttt{OFPT\_PACKET\_OUT} message to forward the buffered frame. Concurrently, the controller may issue an \texttt{OFPT\_FLOW\_MOD} message to install a matching flow entry in the switch's flow table.

Subsequent packets belonging to the same flow match the installed entry directly in hardware or kernel space (such as Open vSwitch datapath), bypassing the controller entirely. The controller can monitor data-plane activity by issuing multipart \texttt{OFPMP\_FLOW} requests to poll flow statistics. Switches respond with \texttt{OFPMP\_FLOW} replies containing packet and byte counters for currently active flow entries. When an entry exceeds its idle or hard timeout, the switch evicts it and may send an \texttt{OFPT\_FLOW\_REMOVED} notification. 

Crucially, the granularity of information visible to the controller via flow statistics is entirely dictated by the match fields specified in preceding FlowMods by the forwarding application. If an application installs coarse MAC-pair entries (\texttt{in\_port, eth\_src, eth\_dst}), all transport connections and IP flows between those two endpoints aggregate into a single counter. Conversely, if an application installs granular 5-tuple entries, flow table occupancy increases dramatically, exposing switches to flow-table saturation attacks.

\subsection{Pitfalls in Machine Learning Security and Network Datasets}
The vulnerability of supervised machine learning to subtle experimental artifacts in computer security was seminalized by Sommer and Paxson~\cite{sommer2010outside}. More recently, Arp et al.~\cite{arp2022dos} systematized ten common pitfalls in security ML, emphasizing sampling bias, data snooping, and spurious correlations.

In network intrusion detection specifically, benchmark datasets have faced substantial scrutiny. Engelen et al.~\cite{engelen2021troubleshooting} discovered critical flow construction, labeling, and TCP sequence errors in CICIDS2017, explicitly warning that non-statistical identifier columns (such as Flow IDs, IP addresses, and timestamps) allow classifiers to memorize host identities rather than attack patterns. Lanvin et al.~\cite{lanvin2022errors} and Liu et al.~\cite{liu2022error} demonstrated that correcting label and orchestration bugs significantly shifts published model rankings. Flood et al.~\cite{flood2024baddesign} surveyed seven benchmark datasets (excluding SDN datasets) and introduced the concept of ``bad design smells,'' proving that standard randomized train/test splits result in widespread cross-split leakage due to synthetic traffic homogeneity. Roy et al.~\cite{roy2026unmasking} demonstrated analogous shortcut learning dynamics on IoT intrusion benchmarks.

\subsection{Intrusion Detection in SDN Environments}
Early SDN security research focused on leveraging control-plane events to mitigate volumetric denial-of-service attacks. Braga et al.~\cite{braga2010lightweight} proposed lightweight DDoS detection using 6-tuple flow statistics polled from NOX controllers. Mousavi and St-Hilaire~\cite{mousavi2015early} utilized PacketIn entropy variations for early DDoS detection. To protect the SDN control plane against saturation attacks, architectures such as AVANT-GUARD~\cite{shin2013avantguard}, FloodGuard~\cite{wang2015floodguard}, and SPHINX~\cite{dhawan2015sphinx} introduced connection migration and flow-table constraint validation.

With the release of benchmark datasets such as InSDN~\cite{elsayed2020insdn}, research shifted heavily toward applying advanced deep learning models to flow-level CSV features. Ataa et al.~\cite{ataa2024intrusion} evaluated CNN-LSTM and Transformer architectures on InSDN, reporting accuracies up to 99.02\%. Ahmad et al.~\cite{optixgb2026} proposed OptiXGB-IDS, combining WGAN-GP oversampling with XGBoost to achieve 99.87\% accuracy on InSDN. Sajid et al.~\cite{sajid2025ddos} reported 99.98\% accuracy using optimizer-equipped CNN-MLPs. Ashikuzzaman et al.~\cite{ashikuzzaman2026sdnguardstack} introduced SDNGuardStack, reporting 99.98\% accuracy using stacked ensemble learning. However, as we document in Section~\ref{sec:lit_audit}, these works evaluate models exclusively on offline flow records and rely on randomized flow-level splits, leaving their operational validity unexamined.

\section{Threat Model and Problem Formulation}\label{sec:threat}
\subsection{System Architecture and Telemetry Semantics}
Consider an SDN architecture comprising a set of OpenFlow switches $\mathcal{S}$ controlled by a logically centralized controller $\mathcal{C}$ over OpenFlow~1.3 control channels. The data plane carries traffic between end hosts $\mathcal{H} = \mathcal{H}_{\text{benign}} \cup \mathcal{H}_{\text{attack}}$.

The control channel between switch $s \in \mathcal{S}$ and controller $\mathcal{C}$ carries a discrete sequence of timestamped OpenFlow messages:
\begin{equation}
\mathcal{M} = \{(t_i, \tau_i, m_i)\}_{i=1}^N,
\end{equation}
where $t_i \in \mathbb{R}^+$ denotes the arrival timestamp, $\tau_i$ denotes the message type belonging to the control-plane set $\{\text{PacketIn},$ $\text{PacketOut},$ $\text{FlowMod},$ $\text{FlowRemoved},$ $\text{StatsReply}\}$, and $m_i$ represents the message payload. When $\tau_i = \text{PacketIn}$, $m_i$ encapsulates the arriving frame header $h_i = (\text{mac}_{\text{src}}, \allowbreak \text{mac}_{\text{dst}}, \allowbreak \text{eth\_type}, \allowbreak \text{ip}_{\text{src}}, \allowbreak \text{ip}_{\text{dst}}, \allowbreak p_{\text{src}}, \allowbreak p_{\text{dst}}, \allowbreak \text{proto})$. When $\tau_i = \text{StatsReply}$, $m_i$ conveys flow table records $e_{i,j} = (\text{match}_{i,j}, \allowbreak \text{pkts}_{i,j}, \allowbreak \text{bytes}_{i,j}, \allowbreak \text{dur}_{i,j})$.

\subsection{Problem Formulation: Streaming Window Detection}
Rather than assuming omniscient offline flow records, a controller-side detector operates on discrete time windows of duration $W$. For each window $k$ spanning $[kW, (k+1)W)$, the detector computes a feature vector:
\begin{equation}
\mathbf{x}_k = \phi(\mathcal{M} \cap [kW, (k+1)W)) \in \mathbb{R}^d,
\end{equation}
where $\phi(\cdot)$ extracts observable control-plane metrics. Given a history of $H$ preceding windows, the model infers a binary or multi-class label $\hat{y}_k \in \{0, 1\}$.

\subsection{Data Partitioning Formulations}
To evaluate model generalization, we formalize four partitioning strategies over a dataset $\mathcal{D} = \{(\mathbf{x}_n, y_n, h_n)\}_{n=1}^{|\mathcal{D}|}$, where $h_n \in \mathcal{H}$ denotes the host associated with record $n$:
\begin{enumerate}
    \item \textbf{Random Flow Split:} Partitions $\mathcal{D}$ into disjoint subsets $\mathcal{D}_{\text{train}}$ and $\mathcal{D}_{\text{test}}$ via uniform random sampling. Crucially, the host sets overlap heavily: $\operatorname{Hosts}(\mathcal{D}_{\text{train}}) \cap \operatorname{Hosts}(\mathcal{D}_{\text{test}}) \approx \mathcal{H}$.
    \item \textbf{Held-Out Host Split:} Partitions the host space $\mathcal{H}$ into disjoint subsets $\mathcal{H}_{\text{train}}$ and $\mathcal{H}_{\text{test}}$ such that $\mathcal{H}_{\text{train}} \cap \mathcal{H}_{\text{test}} = \emptyset$. All records belonging to $\mathcal{H}_{\text{train}}$ form $\mathcal{D}_{\text{train}}$, and records belonging to $\mathcal{H}_{\text{test}}$ form $\mathcal{D}_{\text{test}}$.
    \item \textbf{Leave-One-Host-Out (LOHO):} For each host $h^* \in \mathcal{H}$, the test set is defined strictly as $\mathcal{D}_{\text{test}} = \{(\mathbf{x}_n, y_n, h_n) \mid h_n = h^*\}$, while the training set comprises all remaining hosts $\mathcal{D}_{\text{train}} = \{(\mathbf{x}_n, y_n, h_n) \mid h_n \neq h^*\}$.
    \item \textbf{Time-Ordered Split:} For a temporal dataset, records are ordered by timestamp $t_1 \le t_2 \le \dots \le t_N$, and a cutoff $T_{\text{split}}$ defines $\mathcal{D}_{\text{train}} = \{(\mathbf{x}_n, y_n) \mid t_n < T_{\text{split}}\}$ and $\mathcal{D}_{\text{test}} = \{(\mathbf{x}_n, y_n) \mid t_n \ge T_{\text{split}}\}$.
\end{enumerate}

\subsection{Threat Model and Scope}
\textbf{Defender Capabilities:} The defender deploys an intrusion detection module co-located with or tapping the SDN controller interface. The detector inspects solely OpenFlow control-plane traffic $\mathcal{M}$. It possesses no packet taps on data-plane switch ports and cannot read host-side sockets. During any given evaluation epoch, the forwarding application running on the controller is assumed fixed and known, though operational changes or policy adjustments require recalibrating detector thresholds as discussed in Section~\ref{sec:live}.

\textbf{Attacker Model:} The attacker controls one or more compromised end hosts in the network. The attacker initiates network attacks including volumetric flooding (DoS/DDoS), port scanning, service probing, brute-force authentication, web application exploitation, and botnet command-and-control communication. The attacker does not compromise the controller kernel or directly forge control-channel TLS certificates.

\textbf{Out of Scope:} Real-time inline mitigation latency, hardware switch TCAM exhaustion, and adversarial evasion of control-plane telemetry features are outside the scope of this study.

\section{What the Controller Sees in InSDN}\label{sec:gap}
\subsection{Dataset Inventory and Capture Reassembly}
InSDN~\cite{elsayed2020insdn} was generated in a virtualized testbed using Mininet and Open vSwitch (OVS) connected to an ONOS controller~\cite{berde2014onos}. Traffic targets a Metasploitable-2 virtual machine or the OVS switch itself. In addition to releasing CSV flow files, the authors published raw PCAP archives recorded at the target hosts and at the ONOS controller's OpenFlow interface.

We fetched all 44 ONOS controller packet captures directly from the institutional repository, verifying each archive against published SHA-256 digests. As summarized in Table~\ref{tab:inventory}, the 44 captures encompass 11 benign sessions and 33 attack sessions spanning seven distinct attack classes.

\subsection{Match Field Granularity and FlowMod Analysis}
To determine what flow entries were active at the switches, we parsed and decoded every OpenFlow~1.3 multipart flow-statistics reply across all 44 controller captures. Over the entire dataset, only two distinct match structures appear:
\begin{enumerate}
    \item \texttt{eth\_type}: Default punting rules installed by ONOS (80\,464 entry observations). Across all 44 captures, our full flow-table decode shows that these 80\,464 entries partition equally across exactly four EtherTypes (20\,116 observations each): IPv4 (\texttt{0x0800}), ARP (\texttt{0x0806}), LLDP (\texttt{0x88cc}), and BDDP (\texttt{0x8942}). All 80\,464 default entries execute the explicit action \texttt{OFPAT\_OUTPUT: OFPP\_CONTROLLER} (controller port \texttt{0xfffffffd}).
    \item \texttt{(in\_port, eth\_src, eth\_dst)}: Reactive MAC-pair forwarding rules (24\,437 entry observations). All 24\,437 entries specify \texttt{OFPAT\_OUTPUT} to physical switch data ports.
\end{enumerate}
Not a single entry in any flow-statistics reply matches on source IP, destination IP, transport protocol, or transport port numbers. A 5-tuple flow---the fundamental unit labelled in InSDN's CSV---is never represented as an individual counter within the controller's flow table.

To verify whether transient 5-tuple entries could have been installed and deleted between polling intervals, we analyzed all 3\,827 FlowMod messages transmitted by the ONOS controller. 3\,811 FlowMods match strictly on \texttt{(in\_port, eth\_dst, eth\_src)}, 16 match on \texttt{eth\_type}, and exactly zero FlowMods specify IP addresses or transport ports. These FlowMods are consistent with an Ethernet learning switch; IPv4 reaches the controller through the punt rule described below.

\subsection{Dynamics of the Controller PacketIn Stream}
The controller's visibility of data traffic comes from PacketIns generated by ONOS's default punting rules and by reactive-forwarding misses. The flow-table decode shows an \texttt{eth\_type=0x0800}$\rightarrow$\textsc{controller} rule in all 44 captures: all 20\,116 observations have priority 5, below the MAC-pair rules (all 24\,437 observations at priority 10), while the ARP, LLDP and BDDP punt rules have priority 40\,000. Only 3\,827 FlowMods occur in the 44 captures, and five captures contain none (Metasploitable DDoS SYN and TCP, and the three OVS web-attack captures); their flow-statistics replies nevertheless show MAC-pair entries (4--73 observations per capture), which were installed before the capture started. We did not establish why packets that such entries should cover still reach the controller; candidates are traffic that matches no installed pair (spoofed or changing address combinations, one-way traffic) and ONOS applications that request packets, but we tested none of them. In Table~\ref{tab:gap} and Fig.~\ref{fig:ratio}, we pair target-side packet counts with controller-side PacketIn volume across all attack scenarios.

In 9 of 12 attack scenarios, the controller receives between 0.68 and 1.29 PacketIns per data packet recorded at the target. Two Metasploitable-2 scenarios show 3.9 and 15.7. The OVS DDoS scenario shows 0.08 (6.5M target packets against 541k PacketIns), consistent with an untested hypothesis of control-channel saturation under a spoofed flood; we did not test this directly. The two sides are separate recordings and their alignment is unverified, so ratios are indicative, not exact per-packet counts. The Normal group has no target-side captures, so we have no such ratio for benign traffic. Because each PacketIn carries the packet's headers, the 5-tuple is visible to the controller per packet, but never as a per-flow counter in the switch flow table.

\textbf{Software flow reconstruction from PacketIns.} Because PacketIns carry packet headers, a monitor could try to reassemble 5-tuple flow records in software. We implemented a streaming reassembler (symmetric 5-tuple key, 120\,s timeout, FIN/RST termination, i.e.\ CICFlowMeter's defaults) and ran it on one capture per scenario, comparing the result with the benchmark CSV (Table~\ref{tab:recon}, \texttt{packetin\_reconstruction.json}). Three observations stand out. (i) In spoofed volumetric attacks and scans almost every reconstructed flow is a single packet (OVS DDoS 100.0\%, OVS Probe 97.3\%). The target-side traces show the same structure (6\,510\,923 packets over 6\,508\,402 distinct 5-tuples for OVS DDoS, Table~\ref{tab:gap}), so this reflects the traffic and not information lost in the control channel. The benchmark CSV, by contrast, contains no single-packet flow in any of the six subsets examined, and for the two OVS captures we found no 5-tuple in common with it (Protocol and ports are zero in all OVS DDoS rows; for OVS Probe the cause is not established), so no accuracy statement is possible there. (ii) Where flows can be matched, rank agreement of packet counts is high on probing ($\rho=0.86$) and benign traffic ($\rho=0.94$) but weak on the DoS capture ($\rho=0.24$, covering 1.7\% of its reconstructed flows), and reconstructed packet totals are 38\% (DoS) and 45\% (benign) of the host-side totals, so the controller sees only a fraction of the packets of the flows it reassembles; on probing the totals agree (ratio 1.00). (iii) Durations are not reliably recovered: rank correlation is 0.98 on the benign capture, but $-0.27$ on DoS and $-0.11$ on probing, where almost all durations are near zero. We did not test why durations diverge under flooding (queueing or buffering of PacketIns is one candidate). The evidence shows only that, with this reassembler and these captures, software reconstruction recovers packet counts and durations in some scenarios and not in others. Matched flows are a subset of the reconstructed flows (Table~\ref{tab:recon}), the benign row is one of eleven captures, and the CSV is a separate recording whose alignment with the controller capture is unverified.

\section{Controller-Observable Intrusion Detection}\label{sec:method}
\subsection{Streaming OpenFlow 1.3 Parser}
We implemented a streaming OpenFlow~1.3 parser designed to reassemble TCP streams on port 6653. The parser handles message boundary segmentation and employs heuristic desynchronization recovery. If a message header is corrupted or desynchronized, the parser scans forward until it discovers two consecutive valid OpenFlow headers. Across all 44 captures, the parser processed 7\,381\,679 messages, requiring only 134 resynchronizations and discarding 12\,217 bytes in total.

\subsection{Feature Engineering}
For consecutive non-overlapping windows of duration $W \in \{1\text{s}, 5\text{s}\}$, we extract 22 controller-observable features:
\begin{itemize}
    \item \textbf{Control Message Counts (5):} Total counts of PacketIn, PacketOut, FlowMod, FlowRemoved, and FlowStats replies.
    \item \textbf{Header Diversity and Distributions (9):} Distinct source MACs, destination MACs, source IPs, destination ports; fractions of TCP, UDP, ICMP, and ARP traffic; and mean frame length.
    \item \textbf{Protocol and Entropy Metrics (3):} TCP SYN-only packet fraction, Shannon entropy of source IPs, and Shannon entropy of destination ports.
    \item \textbf{Flow Table Counter Deltas (5):} Number of active entries reported in statistics replies, sum and maximum of packet deltas, and sum and maximum of byte deltas between consecutive polls.
\end{itemize}
To capture temporal dynamics, the feature vector concatenates the current window with three preceding windows ($H=4$), applying a $\log(1+x)$ transformation to normalize dynamic ranges.

\subsection{Strict Ground-Truth Window Labeling}
Assigning ground-truth labels to controller windows requires precision. Marking every window within an attack capture as malicious would mislabel idle periods. Instead, we match the 5-tuple header of every PacketIn message against InSDN's ground-truth CSV flow records.

A window is labelled as an attack window if and only if it contains at least one PacketIn matching a known attack flow. In attack captures, windows containing unmatched IP traffic are marked as ambiguous and excluded from training and evaluation. Benign captures retain all windows. As shown in Table~\ref{tab:inventory}, this strict protocol yields a sparse set of verified attack windows for low-volume classes (e.g., 6 windows for Brute Force, 12 for Exploit).

Two consequences of this construction shape everything that follows. First, a label requires the CSV to carry a usable 5-tuple. In \texttt{OVS.csv} all 48\,413 DDoS rows have Protocol, source port and destination port set to 0, so no PacketIn can match them, and the three OVS DDoS captures contribute no attack windows. The two OVS brute-force captures also contribute none: their CSV rows target the container address 172.17.0.2 and we found no PacketIn with a matching 5-tuple (the cause is not established). Second, the labelled attack windows are dominated by probing: Table~\ref{tab:deployment} shows that probe windows are 75.9\% of all 2\,589 attack windows, and the two Metasploitable-2 probe captures alone supply 1\,922. Pooled scores are therefore close to probe-detection scores, and per-class results must be read with these counts in mind. By construction, attack windows are windows in which at least one CSV-matched flow crossed the controller; this selection may favour easy windows, and we cannot quantify that effect here.

\subsection{Evaluated Models and Baselines}
We evaluate several detector architectures:
\begin{itemize}
    \item \textbf{Multi-Layer Perceptron (MLP):} A fully connected network (64--32 units, ReLU activation, dropout rate 0.2, class-weighted cross-entropy loss, Adam optimizer, 40 epochs).
    \item \textbf{Linear Classifier:} Logistic regression with L2 regularization operating on the same historical feature inputs.
    \item \textbf{Single-Window MLP:} An MLP evaluating only the current 1\,s window without temporal history.
    \item \textbf{Feature-Ablated MLPs:} Models trained exclusively on PacketIn-derived features or flow-statistics features.
    \item \textbf{Threshold Heuristics:} Univariate decision thresholds fitted on training folds (PacketIn rate, normalized burst rate, source-IP entropy, destination-port entropy).
    \item \textbf{Gradient Boosted Trees (XGBoost):} An optimized XGBoost baseline trained on the GPU using the same window features.
    \item \textbf{Host-Side Flow Baseline:} XGBoost trained on InSDN's 78 numeric CICFlowMeter features, which include the source and destination port numbers, under standard 70:30 flow splits. The audit of Section~\ref{sec:audit} repeats the split without ports, IP addresses, Flow ID and timestamps (77 features).
\end{itemize}

\subsection{Validation Protocols}
All evaluations enforce capture-level separation: no capture file appears in both training and testing sets. Metrics are reported across 10 random seeds as mean with 95\% $t$-interval over seeds. For P1 each seed draws a new capture-to-fold assignment and a new network initialization, so this interval reflects both and not the sampling of captures; the capture-level cluster bootstrap in Table~\ref{tab:boot} addresses the latter. The three detection protocols are:
\begin{itemize}
    \item \textbf{P1 (Capture-grouped 5-fold CV):} Captures are partitioned into five folds, stratified by class.
    \item \textbf{P2 (Withheld attack families):} Entire attack families are held out (DoS and DDoS pooled as flooding); benign captures are split 70:30 between training and testing.
    \item \textbf{P3 (Cross-deployment transfer):} Training on Metasploitable-2 sessions and testing on OVS sessions, and vice versa; benign captures are split 70:30 as in P2.
\end{itemize}
We report Balanced Accuracy (BAcc), Recall, and False Positive Rate (FPR). The evaluation-validity audit of Section~\ref{sec:audit} uses its own protocols A--E.

\section{Empirical Detection Results}\label{sec:results}
\subsection{Performance on Unseen Captures}
Table~\ref{tab:cv} presents detection results on unseen captures under 5-fold cross-validation ($W{=}1$\,s). Across 10 seeds (Section~\ref{sec:method}), the controller-observable MLP achieves a balanced accuracy of $0.946\pm0.016$ with a false positive rate of 0.001. Logistic regression performs competitively at 0.939, and the single-window MLP reaches 0.934, indicating that temporal history provides marginal separation gain in this feature space.

In contrast, standard SDN heuristics perform poorly: the PacketIn-rate threshold achieves only 0.616 balanced accuracy (FPR 0.561), failing because benign interactive sessions also generate bursty PacketIn streams. Entropy thresholds perform substantially better (0.839--0.852). Ablation confirms that PacketIn features drive performance (0.943 alone), while flow-statistics features alone achieve only 0.699 with an FPR of 0.284, consistent with coarse MAC-pair aggregation.

While Table~\ref{tab:cv} reports variation across seeds ($\pm0.016$; each seed redraws the capture-to-fold assignment and the initialization), a cluster bootstrap resampling over captures (Table~\ref{tab:boot}) measures capture-level variance, yielding a pooled BAcc of 0.984 [0.926, 0.995] for the MLP. A label-shuffle sanity check produces a balanced accuracy of $0.512\pm0.054$ at 1\,s and $0.508\pm0.067$ at 5\,s, i.e., chance level; this confirms that the featurization pipeline does not inadvertently encode label information directly, though it does not address session-level confounding.

\subsection{Withheld Attack Families and Cross-Deployment Transfer}
Under leave-one-attack-family-out testing (Table~\ref{tab:family}), the controller-side MLP reaches 0.936 on floods, 0.997 on probes and 0.904 on web attacks, above the best single-feature threshold in those families; these scores are subject to the session confound of Section~\ref{sec:confound}. On sparse minority classes, thresholds or linear models match or exceed it (e.g., botnet threshold 0.965 vs.\ MLP 0.932; logistic regression 0.997 on exploit). The brute-force, exploit and web families rest on only 6, 12 and 12 attack windows (Table~\ref{tab:deployment}), so their scores carry uncertainty that the seed interval does not capture. In cross-deployment evaluations (Table~\ref{tab:cross}), training on OVS sessions and testing on Metasploitable-2 yields 0.990 balanced accuracy, while the reverse direction achieves 0.905 (with logistic regression reaching 0.928). The OVS$\rightarrow$Metasploitable-2 direction is scored on 2\,128 attack windows, 1\,922 (90\%) of them probe windows; the reverse direction is scored on 461 OVS attack windows (botnet 83, DoS 323, probe 43, web 12). Extending the window length to $W{=}5$\,s yields consistent performance (MLP 0.958, logistic regression 0.961, XGBoost 0.952).

\subsection{Comparison with Host-Side Flow Baseline}
For contrast, applying XGBoost to InSDN's host-side CICFlowMeter features (343\,889 rows, 78 numeric features including the two port numbers) under standard randomized 70:30 flow splits yields a balanced accuracy of $0.9998\pm0.00003$. This near-perfect accuracy should not be read as evidence of detection ability: Section~\ref{sec:audit} shows that it does not survive host-held-out evaluation on this dataset.

\section{Validity Analysis: Disentangling Attacks from Session Artifacts}\label{sec:confound}
\subsection{The Trivial IP PacketIn Rule}
In the distributed captures, benign and attack traffic were recorded in separate sessions, and the attack sessions contain no identifiable concurrent benign background traffic (see the window counts below). Strict labelling therefore confounds session type with the label.

When we evaluate the MLP strictly within attack sessions, it achieves a pooled balanced accuracy of 0.942 (macro-averaged 0.906). However, a trivial baseline rule---``classify window as attack if it contains at least one IP PacketIn''---achieves a pooled balanced accuracy of 0.995 and a macro-averaged score of 1.000 across the exact same windows (Fig.~\ref{fig:scores}). This 0.995 score reflects the labeling protocol combined with session separation: because the ambiguity mask excludes attack-session windows containing unlabelled IP traffic, the surviving attack-free windows contain almost no IP traffic. Of the 2\,178 attack-free windows kept in attack sessions, 1\,858 are empty (no PacketIn at all) and are excluded from this metric; of the remaining 320, 317 contain no IP PacketIn (ARP, LLDP or other non-IP frames). The 0.995 therefore rests on 2\,589 attack windows and 320 attack-free windows. Thus, any rule checking for the presence of IP packets achieves near-perfect separation inside attack sessions without learning any attack characteristics.

\textbf{Operational Evaluation across Benign Traffic.} While the trivial rule exploits this non-interleaved benchmark artifact within attack sessions, evaluating it against operational benign traffic (the 11 Normal sessions, 33,283 windows) exposes its failure mode (\texttt{operational\_stream\_evaluation.json}): because 77.5\% of normal-session windows contain IP PacketIns (25,810 of 33,283 windows), the trivial rule flags 77.5\% of normal-session traffic as attacks (normal-session FPR = 0.775). Evaluated on the full strict labeled window set (38,050 windows: 2,589 attack, 35,461 pooled benign), every attack window contains an IP PacketIn by construction of strict labels (Recall = 1.000), but its overall benign FPR of 72.8\% drops balanced accuracy to 0.6360 (and to 0.4889 across the raw unmasked 42,099-window stream). In contrast, the controller-observable MLP avoids triggering on benign IP traffic, achieving a false positive rate of only 0.001 on normal sessions and 0.946 balanced accuracy overall (Table~\ref{tab:cv}). However, as our session probes demonstrate below, avoiding simple heuristic triggers does not mean the MLP has learned invariant attack semantics: classifiers trained on residual traffic stripped of all attack PacketIns still predict session origin with 0.940 balanced accuracy (Table~\ref{tab:confound}). Thus, non-interleaved benchmark recordings make it difficult to untangle genuine attack detection from controller-level session fingerprints.

\subsection{Host-Identity Baseline}
To bound how much of the controller-side score can be explained by \emph{which hosts appear}, without any traffic statistics, we evaluate two rules learned on the training captures of each fold (same folds, labels, windows and seeds as Table~\ref{tab:cv}). Rule R1 predicts attack if the window contains a PacketIn source address that appeared in training attack windows and in no training attack-free window; rule R2 predicts attack if it contains any source address seen in training attack windows (\texttt{session\_identity\_baseline.json}). Table~\ref{tab:identity} shows that R1 reaches a balanced accuracy of 0.734 over all strictly labelled windows, with recall limited to 0.472 because the source addresses of spoofed floods never repeat across captures, and that R2 (0.680) is dominated by false positives on benign sessions. Within attack sessions R2 is again near-perfect (0.994), like the any-IP rule.

Host identity therefore explains a substantial part of the separation but not all of it: the MLP exceeds R1 by 0.21 balanced accuracy, so its score is not reducible to address memory. However, the session probe below still separates sessions at 0.940 after attack-matched PacketIns are removed, so we cannot attribute the remaining margin to attack semantics rather than to other session fingerprints such as traffic mix or timing. The rules are simple; a stronger identity model could score higher, so these numbers are lower bounds on what identity can explain.

\subsection{Session Probes}
To test whether classifiers recognize session identity rather than attack signatures, we trained an MLP on windows where all attack-matched PacketIns were excised (Table~\ref{tab:confound}). The model predicts whether a window originates from an attack session with 0.940 balanced accuracy (D1). When restricted to attack-free windows (D2), it achieves 0.950. However, 82\% of these residual windows contain unmatched IP traffic that likely represents unlabelled attack remnants, and D2 rests on only 6 windows from 2 captures. These findings demonstrate that in non-interleaved benchmark recordings, attack detection cannot be cleanly disentangled from session fingerprinting.

\section{Evaluation-Validity Audit: Random Flow Splits vs.\ Held-Out Hosts}\label{sec:audit}
\subsection{Experimental Design Across Two Benchmarks}
To evaluate leakage in flow-based evaluations, we implemented a standardized evaluation pipeline applied to two prominent benchmarks: InSDN (343\,889 flows) and an external reference dataset, CICIDS2017 (2\,100\,814 flows). We evaluate an identical GPU-accelerated XGBoost classifier across four distinct protocols using 10 random seeds (Table~\ref{tab:audit} and Fig.~\ref{fig:split}):
\begin{itemize}
    \item \textbf{Protocol A (Random 70:30 Flow Split):} Standard randomized flow-level partition. Excludes all IP addresses, ports, Flow IDs, and timestamps (retaining 77 numeric features).
    \item \textbf{Protocol B (Held-Out Source Hosts):} 70:30 partition grouped by source IP. No source host appears in both training and test sets.
    \item \textbf{Protocol C (Time-Ordered Split):} Deterministic 70:30 chronological partition per capture file.
    \item \textbf{Protocol D (Identifier-Only Split):} Random 70:30 split trained exclusively on IP addresses, port numbers, and Flow IDs.
    \item \textbf{Protocol E (Redundancy Audit):} Measurement of the percentage of test-set rows that possess an exact feature duplicate in the training set under Protocol A.
\end{itemize}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{fig_split.pdf}
\caption{Balanced accuracy across four evaluation protocols on InSDN and CICIDS2017 (10 seeds; dots represent individual host splits). When source hosts are held out, performance degrades sharply, and identifier-only models achieve near-perfect scores.}\label{fig:split}
\end{figure}

\subsection{The Generalization Collapse on Unseen Hosts}
Under Protocol A (random flow split), XGBoost achieves near-perfect balanced accuracy: 0.9998 on InSDN and $0.9917\pm0.0001$ on CICIDS2017. However, under Protocol B (held-out source hosts), performance on InSDN drops by nine percentage points to $0.907\pm0.085$, with individual splits swinging from 1.00 down to 0.66. Across the 10 random seeds on InSDN, the balanced accuracy distribution is widely dispersed: five seeds score near 1.00 (0.996, 0.998, 0.999, 1.000, 1.000), two score between 0.85 and 0.94 (0.859, 0.939), and three drop below 0.84 (0.660, 0.786, 0.837), consistent with the acute host concentration documented below. On CICIDS2017, the drop is catastrophic: performance collapses by 35 percentage points to $0.641\pm0.056$. A per-file time-ordered split shows no drop on InSDN (0.9997) but falls to 0.719 on CICIDS2017. We did not analyze why; CICIDS2017's attacks were run in scheduled time slots~\cite{sharafaldin2018cicids}, so a chronological cut can withhold an attack phase, which would be consistent with the drop.

Under Protocol D, a classifier supplied exclusively with network identifiers (IP addresses, ports, and Flow ID) achieves 1.0000 on InSDN and 0.9999 on CICIDS2017. Network identifiers alone therefore separate the classes in these benchmarks; this does not show that models trained on flow features use them, only that they could.

\subsection{The Role of Data Redundancy and Class Coverage}
Under Protocol E, we discover that 48.7\% of random-split test rows in InSDN (and 20.3\% in CICIDS2017) are exact duplicates of training rows. To test whether duplicate flows drive the random-split score, we deduplicated InSDN completely, reducing the dataset from 343\,889 to 184,607 rows. On this deduplicated dataset, the random-split score remains unchanged at 0.9998. Thus, feature redundancy alone does not explain the performance gap.

To ensure that host grouping does not artificially penalize performance by withholding entire attack classes from training, we enforced a class-coverage constraint: holding out source hosts while guaranteeing that every attack class appears in the training partition. Under this controlled setting, balanced accuracy is 0.939 (0.812 after deduplication). Grouping by the 3-tuple \texttt{(src\_ip, dst\_ip, dst\_port)} yields 0.961 (0.984 after deduplication). The triple-grouped split fragments traffic while retaining communication from the same attacker hosts on different ports across partitions, allowing the model to leverage host-level similarities without exact flow duplication.

\subsection{Host Concentration and the Held-Out-Host Dispersion}
Why do held-out-host scores vary so widely? InSDN contains 122,868 distinct source IP addresses; however, 122,307 of these source IPs appear in exactly one flow record, generated during spoofed DoS/DDoS flooding. Crucially, only eight hosts account for 500 or more flows, yet these eight hosts encompass 215,404 of InSDN's 343,889 total rows. Among these eight dominant hosts, exactly three source attack-labelled flows.

By logging host assignments across all 10 evaluated Protocol~B seeds (\texttt{host\_assignment\_audit.json}), we observe that the balanced accuracy dispersion correlates with dominant host allocations:
\begin{itemize}
    \item Assigning the primary attacker host \texttt{200.175.2.130} (110\,799 flows, 32.2\% of the dataset) to test (Seeds 0 and 1) elevates test share to 43.7\% and 57.1\%, dropping balanced accuracy to 0.786 and 0.660.
    \item When the primary benign host \texttt{192.168.20.133} (53\,790 flows, 15.6\% of the dataset) is assigned to test (Seeds 4 and 7), balanced accuracy drops to 0.859 and 0.837 due to false positives on unseen benign activity.
    \item When neither primary host is withheld, performance is generally high: Seeds 3, 5, 6, 8, and 9 score between 0.996 and 1.000 (test row share 11.2\%--22.1\%). The one intermediate case is Seed 2 (BAcc 0.939, test share 22.2\%), where neither primary host is in test. Host \texttt{192.168.20.1}, which yields an 18.8\% FPR when held out alone (leave-one-host-out, below), is in the test set of Seed 2 (and of Seed 0), which is consistent with the intermediate score; we have not verified the role of this host.
\end{itemize}
The 0.66--1.00 range is consistent with the uneven allocation of these few dominant hosts across splits, as are the leave-one-host-out results below. With ten correlated splits this is an association, not an identification of cause.

To quantify generalization to individual hosts, we conducted a Leave-One-Host-Out (LOHO) evaluation, holding out one dominant host at a time while training on all remaining records. When holding out the primary attacker (host 200.175.2.130), the model catches only 51.6\% of its attack flows (DoS detection recall collapses to 34.7\%). Conversely, when holding out the largest benign host (host 192.168.20.133), the false positive rate spikes to 37.9\%. On CICIDS2017, which contains 48 source IPs (15 with $\ge 500$ flows), holding out the primary attacker (172.16.0.1, 442\,098 flows) results in an attack recall of only 28.3\% and a benign false positive rate of 54.0\%. Individual bot hosts held out in isolation achieve detection rates between 23.4\% and 43.5\%.

\subsection{Replication of Published Pipeline (SDNGuardStack)}
We partially replicated the published SDNGuardStack pipeline~\cite{ashikuzzaman2026sdnguardstack} using our own implementation across 5 seeds. Under a random split, the model reproduces its published performance, achieving 0.9999 accuracy (published: 99.98\%). However, under held-out source hosts, mean accuracy drops to 0.72 when selecting features strictly on training folds (per-seed: 0.24, 0.73, 1.00, 0.66, 0.99) and 0.78 when selecting on all rows (per-seed: 0.33, 0.99, 1.00, 0.62, 0.98); 95\% confidence intervals span up to $\pm 0.39$. The metric is 8-class accuracy. This dispersion is consistent with InSDN's host concentration: a 20\% host partition draws hosts with very unequal traffic volumes, the test row share varies from 8\% to 40\% across seeds, and the lowest score (0.24) occurs in the run with the largest test partition (40\% of all rows), consistent with the test fold being dominated by a few large hosts while no test class is absent from training (\texttt{unseen\_test\_share} is 0.0 in all seeds). We did not test this attribution further.

\section{Targeted Literature Audit and Feature-Recipe Evaluations}\label{sec:lit_audit}
\subsection{Targeted Audit of SDN-IDS Literature}
To assess how prevalent these evaluation flaws are in the SDN-IDS literature, we conducted a targeted audit of 12 representative papers (eleven focusing on SDN or InSDN, and one non-SDN control). As documented in Table~\ref{tab:lit_audit}, ten papers were read in full text.

Our audit finds recurring methodological gaps:
\begin{enumerate}
    \item \textbf{Absence of Host Grouping:} Among all InSDN papers read in full, none reports a host-grouped or capture-grouped validation split. Most employ simple randomized partitions (such as \texttt{train\_test\_split}) or fail to document their split mechanism entirely.
    \item \textbf{Use of Network Identifiers as Model Inputs:} Three papers explicitly include non-generalizable network identifiers (Flow IDs, IP addresses, or port numbers) among their feature sets. Notably, SDNGuardStack~\cite{ashikuzzaman2026sdnguardstack} ranks Flow ID, Source IP, and Destination IP as the most important features via mutual information and SHAP analysis. Similarly, OptiXGB-IDS~\cite{optixgb2026} and Sajid et al.~\cite{sajid2025ddos} retain destination port, which emerges as the dominant decision feature.
    \item \textbf{Offline Evaluation of Controller Claims:} Multiple papers frame their models as lightweight controller-side defenses, yet evaluate exclusively on offline CSVs without deploying within an SDN controller.
\end{enumerate}

\subsection{Feature-Recipe Evaluations on InSDN}
To determine whether the evaluation gap is specific to feature selection, we implemented four generic feature recipes approximating choices in the literature, evaluated with GPU XGBoost across 10 seeds (Table~\ref{tab:recipe}):
\begin{enumerate}
    \item \textbf{Numeric features only (77 features):} Random split achieves 0.9998 BAcc (0.9991 8-class); held-out source hosts drops to 0.943 BAcc (0.788 8-class).
    \item \textbf{Numeric + ports (79 features):} Random split achieves 0.9998 BAcc (0.9998 8-class); held-out source hosts drops to 0.856 BAcc (0.687 8-class).
    \item \textbf{Numeric + identifiers (83 features):} Random split achieves 1.0000 BAcc (0.9999 8-class); held-out source hosts drops to 0.941 BAcc (0.804 8-class).
    \item \textbf{Top-15 by Mutual Information:} Selected on full data prior to splitting. Mutual information automatically selects Flow ID, Src IP and Dst IP. Random split achieves 1.0000 BAcc (0.9999 8-class); held-out hosts drops to 0.941 BAcc (0.835 8-class, widest CI 0.241).
\end{enumerate}
Across all recipes, random splits achieve near-perfect scores ($\ge 0.9998$), but performance degrades under host-grouped evaluation. Under host grouping, adding identifier columns yields 0.941, comparable to numeric features alone (0.943), which is consistent with decision trees relying on numeric features when test-set IPs are unseen. However, under random splits, computing mutual information across the unpartitioned dataset selects Flow ID, Src IP and Dst IP among the top features, enabling near-perfect scores (1.0000) by memorizing training-set identifiers across partitions.

\section{Methodological Guidelines and Evaluation Checklist}\label{sec:guidelines}
To improve rigor in SDN intrusion detection research, we propose seven concrete methodological guidelines:
\begin{enumerate}
    \item \textbf{Verify Controller Observability:} Researchers proposing controller-side defenses must verify that input features correspond to OpenFlow control-plane primitives. If features require full-packet timing moments, the architectural cost of data-plane polling or flow-table modifications must be explicitly accounted for.
    \item \textbf{Enforce Topology-Aware and Host-Disjoint Splits:} Standard random flow splits should not be used to evaluate generalizable detection. Datasets must be partitioned such that source hosts in the test set are completely withheld from training ($\mathcal{H}_{\text{train}} \cap \mathcal{H}_{\text{test}} = \emptyset$).
    \item \textbf{Purge Non-Generalizable Network Identifiers:} All non-statistical network metadata (such as Flow IDs, IP addresses, MAC addresses, and ephemeral transport ports) must be removed prior to feature extraction.
    \item \textbf{Audit Dataset Host Concentration:} Authors must report the distribution of flows per host. In datasets where a handful of hosts dominate total volume, Leave-One-Host-Out (LOHO) testing should be reported alongside aggregate metrics.
    \item \textbf{Report Redundancy Audits:} Report the share of test rows that duplicate training rows, and results with and without cross-split duplicates removed. In our data, removal left random-split scores unchanged and moved host-grouped scores in both directions, so both should be shown.
    \item \textbf{Evaluate Forwarding Application Sensitivity:} Detectors relying on control-plane metrics (such as PacketIn rates) must evaluate sensitivity to forwarding application policies, entry granularity, and idle timeout configurations.
    \item \textbf{Report Session-Identity Baselines and Label Coverage:} When benign and attack traffic are recorded in separate sessions, report trivial identity rules (an any-IP rule and a host-memory rule learned on training data), the attack windows per deployment and class, and, where possible, record benign and attack traffic interleaved.
\end{enumerate}

\section{Discussion and Limitations}\label{sec:discussion}
\subsection{Scope and Experimental Boundaries}
The controller-side results concern one benchmark (InSDN), one controller (ONOS with its default reactive forwarding) and two deployments (Metasploitable-2 and OVS). CICIDS2017 is a non-SDN reference used only for the split analysis. The split analysis uses one classifier family (XGBoost) on flow features, and other architectures may respond differently. We attempted a third candidate, UKMDDoSDN~\cite{ukmddosdn2025}, but its public PCAPs contain no benign traffic and no OpenFlow control channel (Appendix~\ref{app:ukm}). We frame this work as a measurement study and methodological critique, not as a deployable end-to-end detector.

\subsection{Threats to Validity}
\textbf{Construct validity.} Window labels come from matching PacketIn 5-tuples to CSV records that were produced from separate end-host recordings; the alignment of the two recordings is unverified. Labelled attack windows are those in which a CSV-matched flow crossed the controller, which may favour easy windows, and OVS DDoS and OVS brute-force have no labelled attack windows (Table~\ref{tab:deployment}).

\textbf{Internal validity.} Seed intervals reflect initialization and fold assignment, not the sampling of captures (the capture-level bootstrap addresses the latter). The host-held-out results rest on ten correlated splits in which eight hosts hold 63\% of the rows, so the host logging shows an association, and leave-one-host-out is a single case per host. Our flow reassembler follows CICFlowMeter's default expiration rules but is not CICFlowMeter, and part of the mismatch with the CSV may stem from that difference. The host-identity rules are simple, so their score is a lower bound on what identity can explain.

\textbf{External validity.} One dataset, one controller and one forwarding application were studied. The Mininet/Ryu study is benign-only with at most three software switches; proactive rule installation, hardware TCAM limits, multiple controllers and production traffic are not covered.

\subsection{Ground-Truth Labeling Trade-Offs}
Strict 5-tuple matching grounds controller windows in benchmark labels but discards unlabelled traffic in attack sessions. Under an alternative broader rule that labels any window containing IP addresses observed during attacks, overall balanced accuracy is lower (MLP 0.881 at 1\,s, 0.887 at 5\,s), and transfer from OVS to Metasploitable-2 is 0.977 against 0.924 in the reverse direction.

\subsection{Deployment Feasibility}
An operational controller-side detector would inspect the control channel through port mirroring or controller event handlers. In our testbed, forwarding granularity and idle timeout change PacketIn volume by two to three orders of magnitude (Section~\ref{sec:live}). Detectors built on PacketIn rates may therefore need recalibration when the forwarding application changes; we did not evaluate any detector under a different forwarding mode, so this is a hypothesis and not a result.

\section{Conclusion}\label{sec:conclusion}
We audited what an SDN controller observes in InSDN and how that benchmark is evaluated. In the 44 ONOS captures, no flow-table entry or FlowMod matches IP addresses or ports, so per-flow counters are absent, while an IPv4 punt rule delivers packet headers to the controller; software reassembly of flows from those PacketIns is partial. A controller-side MLP reaches 0.946 balanced accuracy on unseen captures, but because benign and attack traffic were recorded in separate sessions, trivial rules based on IP presence or on host identity explain much of the separation, and the score cannot be read as attack detection. Under strict labelling, whole deployment--class cells (OVS DDoS, OVS brute-force) carry no attack windows and probing dominates the rest.

On flow features, random splits give $\geq 0.9917$ balanced accuracy on both InSDN and CICIDS2017, whereas holding out source hosts gives $0.907\pm0.085$ and $0.641\pm0.056$; the InSDN dispersion is consistent with which of eight dominant hosts is withheld, and leave-one-host-out recall on the primary attacker is 51.6\% (DoS 34.7\%). None of the 12 audited SDN-IDS papers reports a host-grouped split. These results come from one dataset and one controller, and the split analysis confirms known leakage mechanisms on an SDN benchmark rather than introducing a new one. We offer seven evaluation guidelines and release the code and result files so that the measurements can be repeated and challenged.

\section{Candidate Second Datasets Examined}\label{app:ukm}
In addition to InSDN and CICIDS2017, we examined two candidate datasets for control-channel analysis. For UKMDDoSDN~\cite{ukmddosdn2025}, we fetched \path|syn_flood_combined.pcap| (18\,922\,240\,B; 199\,273 packets) and \path|udp_flood_combined.pcap| (15\,420\,748\,B; 110\,518 packets). Parsing confirmed that neither capture contains packets on TCP port 6633 or 6653; they represent data-plane host captures without OpenFlow control traffic, and contain no benign class. For LAN-SDN-NIDS~\cite{lansdnnids2026}, its record describes flow-level records with 11 control-plane metrics, but raw OpenFlow control-plane captures are not available. Neither dataset could support control-channel reassembly.

\section*{Data and Code Availability}
InSDN CSVs and PCAPs are publicly available (sources and SHA-256 digests in \path|data/MANIFEST.md|). The OpenFlow~1.3 parser, feature extraction, evaluation code, the per-experiment result files and the table and figure generators are in the project repository (\url{https://github.com/adhyan-jain/Proteus}, directory \path|research/insdn_controller|). The script \path|reproduce.sh| is provided to regenerate the result files from the raw data (it requires a CUDA GPU), and \path|paper/verify_numbers.py| checks every number quoted in the text against the stored result files. Experiments ran in Python 3.12 with PyTorch 2.11 (CUDA 12.8) and XGBoost 3.4 on one NVIDIA RTX 4060 laptop GPU. Capture hashes are in \path|capture_hashes.sha256|.
